# Writing style

> 改寫自 pstack 的 `unslop` 與 `technical-writing`（MIT，來源與授權見 [`../THIRD_PARTY_NOTICES.md`](../THIRD_PARTY_NOTICES.md)）。原版針對英文，本檔改為正體中文的對應規則。

目標：讀者第一次讀就懂，而且看不出是 AI 寫的。

三條最高原則：

1. **刪掉不做事的字**：句子少了這個字還成立，就刪
2. **用日常用語**：「用」不寫「運用」，「幫助」不寫「協助賦能」
3. **規則讓句子變差時，用別的方式改寫或保持原樣**：每條規則都遵守、但讀起來像機器的句子，等於失敗

以專案本身為詞彙表：寫實際的檔名、指令、欄位名（`inventory.csv`、`npm run check`、`disposition`），不用描述或同義詞代替。

## 先選文件類型（Diátaxis）

一份文件只做一件事。

| 類型 | 讀者在做什麼 | 寫法 | 本專案例子 |
|---|---|---|---|
| 教學 | 第一次學 | 每一步都有看得到的結果，寫出預期輸出 | `docs/onboarding.md` |
| 操作指南 | 要完成某件事 | 只寫步驟，假設讀者有基礎；條件寫在步驟前 | skill 的流程段落 |
| 參考 | 查資料 | 只陳述事實，結構對應被描述的東西，不帶意見 | 欄位定義表、`CLAUDE.md` 指令表 |
| 說明 | 想理解為什麼 | 背景、取捨、替代方案，可以有觀點 | ADR、`content-audit.md` 的規則理由 |

不要混用：參考表不放教學口吻，操作指南不夾帶論述。需要時拆開並互相連結。

## 句子

- 主詞明確，誰做什麼：「script 會寫回三個欄位」，不寫「三個欄位會被寫回」
- 指令用祈使句：「執行 `npm run check`」，不寫「應該要執行」
- 條件放在指令前：「`node_modules` 不存在時，先執行 `npm ci`」
- 一句一件事；超過約 40 字就考慮拆句
- 同一個東西全文只用一個名稱：寫了「處置」就不要再換成「處理方式」「決定」
- 「它」「這」「此」要能明確指到一個名詞，有疑慮就重複名詞
- 數字與結論要能驗證：寫出來源檔案或重現指令
- 標題寫重點，不只寫主題（「先選文件類型」優於「文件類型」）；一頁一個 h1，不跳級
- 有順序的用編號清單，其他用項目符號；清單項目句型一致

## 要刪改的 AI 腔

### 內容

1. **空泛歸因**：「業界普遍認為」「專家指出」→ 寫出來源，或刪掉
2. **套話結尾**：「未來可期」「讓我們拭目以待」「為企業創造更大價值」→ 寫具體的下一步或事實
3. **說感覺不說機制**：「讓管理更輕鬆」→ 寫做了什麼、數字是多少。這句話放到別的專案也成立，就是沒說到這個專案，刪掉

### 用詞

4. **AI 高頻詞**：賦能、助力、深耕、打造（非實體）、無縫、全方位、一站式、極致、引領、致力於、聚焦、生態系（非真實生態系）、底層邏輯、抓手、閉環、賽道 → 換成具體動詞或刪除
5. **「不僅…更…」「不只是…而是…」**：直接說重點
6. **硬湊三點**：不要為了排比湊成三項，有幾項寫幾項
7. **同義詞輪替**：同一段裡「平台」「系統」「解決方案」指同一個東西 → 選一個
8. **虛詞堆疊**：「進行」「加以」「予以」「透過…的方式」「在…的部分」「針對…來做」→ 刪掉，「進行優化」寫成「優化」
9. **過度避險**：「可能或許在某種程度上」→ 「可能」；確定的事就直接寫
10. **翻譯腔**：「一個」濫用、「被」字句、「當…的時候」、「基於…的考量」→ 改成自然中文

### 格式

11. **粗體過多**：只粗體真正要讀者記住的一兩處，不要每個名詞都粗體
12. **「**標籤：** 重述」清單**：粗體標籤後面只是重複標籤內容 → 改成一般句子
13. **裝飾 emoji**：標題與清單不放 emoji（PR attribution 等規定格式除外）
14. **破折號與冒號串句**：「——」與句中冒號當連接詞 → 拆成兩句或用逗號
15. **標點與空格不一致**：中文句子用全形標點（，。：「」）；中文與英文、數字、`code` 之間加一個半形空格，與既有文件一致
16. **聊天腔**：「希望對你有幫助」「當然可以！」「好問題！」→ 刪掉

## 網站文案

網站文案同樣適用以上規則，另外：

- 文案分事實與表述（`CLAUDE.md`「內容規則」）。表述（標題、價值主張、段落敘事、CTA）可以原創，不必照抄現站；事實（數字、客戶名、認證、獎項、功能、成果）只能用事實庫的，用 `fact('<id>')` 或 frontmatter `facts` 引用，不改寫成更強的說法
- 「領先」「第一」「最」「唯一」屬於事實，事實庫有才能用
- 寫客戶得到什麼結果、產品做了什麼，不寫形容詞堆疊
- 產品名、功能名維持官方寫法，不翻譯、不改大小寫

## PR 與 commit

PR 描述與 commit message 也是文件：上述規則都適用（Diátaxis 除外）。PR body 是讓 reviewer 一分鐘內看完的簡報：不貼長 log、SHA 清單或大型數據表，改為連結檔案。

## 範例

改寫前：

> 本次透過全新打造的稽核腳本，針對現站內容進行全方位的盤點與分析，不僅能有效提升內容品質，更能為後續遷移工作賦能。

改寫後：

> `scripts/inventory/audit.mjs` 為 `inventory.csv` 的 1,306 列寫入處置與理由。重爬後執行 `node scripts/inventory/audit.mjs` 即可重算。
