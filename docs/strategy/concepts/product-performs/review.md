## 評審：product-performs

評審日期 2026-11-01，由新的 `reviewer` 依 `site-review` 評分。評審沒有讀本目錄的 `README.md`、`sheet.md` 與其他方向；除了 `shot-*`，另外用 Playwright 開 file:// 截了 1280 與 375 寬的每一屏（reduced motion，截圖不在 repo，理由裡的 s1280-NN、s375-NN 指這組截圖的第 NN 屏）。設計概念階段不判斷通過與否，分數只供選方向。

第一印象：只看第一屏約 5 秒，讀得出「金融與政府的系統，接上 API 與 AI」。說明句第一句是公司名，再加「規範要求直接做在產品功能裡」，所以知道是誰、替誰、做什麼。中間一欄是 digiRunner 主控台：請求依序通過 OAuth 與金融檢查，送進「核心銀行系統」。底下接一張 IBM System/360 大型主機照片，「接進既有系統」的意思很具體。競品的第一屏是發光方塊、手指、光流，這頁換掉 logo 也不會被當成競品。不過第一屏最亮、字最密的是中間的白色介面欄，不是 h1。h1 被拆在左右兩端，兩半之間隔著這一欄，眼睛要跳過去才讀得完整句。

### 設計：平均 3.3

| 項目 | 分數 | 理由 |
|---|---|---|
| D1 第一屏的辨識度 | 4 | h1「金融與政府的系統／接上 API 與 AI」在第一屏寫出服務對象與做的事。說明句以「昕力資訊（TPIsoftware）」開頭；主要 CTA 與「依產業看方案」都在第一屏，375 寬也一樣。影像是介面片段（「轉送：核心銀行系統 已送達」、DigiLism「核心銀行系統或過時大型機的資料轉換」）加大型主機照片，和競品的發光科技物件分得開。沒給 5：介面欄的對比與面積都壓過 h1，讀者第一眼落在介面的小字。1280 寬時介面欄最上面一張卡被 header 切掉一半（「進行分類分級管理」那列），看起來像捲到一半的畫面 |
| D2 與設計原則一致 | 3 | 大部分決定對得上原則：P1，h1 寫產業與做的事，沒有 eyebrow，紫色只用在 logo 與 CTA；P2，產業段的事實照原文排，右側放類別標籤，穩定度段的年份單獨成一欄；P3，介面片段標 `data-ui`，標籤用真的系統名稱；P4，平塗的深色底，沒有漸層與玻璃。輕微違反有三處：一，導入段大標上方的「導入前」用另一個顏色（棕褐色），寫法接近 P1 禁止的 styled accent word 或 eyebrow；二，案例段三張 1903、1922 年布里斯班與美國醫院的老照片很大，卻不是案例本身的文件或場域，比較像氛圍圖，P5 要的是「每段的圖都是這一段的內容」；三，介面片段的下拉選單與分段控制項有 box-shadow（style.css 第 264、273 行），違反 house rule 的 no shadows |
| D3 視覺層級 | 3 | 層級大致清楚，但有幾處互相搶焦點。一，hero：中間白色介面欄搶走 h1 的第一眼。二，案例段：右側 800px 寬的黑白照片比左邊的成果原文（「節省逾80%人工作業時間」）醒目，證據變成配角。三，聯絡段：h2「談需求，或預約 demo」的字級比下面的說明句還小，層級顛倒。四，導入段的「AI 導入情境分析」是全頁最大的字之一，但這段在 brief 的判斷順序裡屬於後段，不該比 hero 與案例重 |
| D4 版面與節奏 | 3 | 各段版型確實不同：hero 三欄；產業段用淺一階的色帶、左標題右列表；案例段左欄 sticky 配大圖；產品段介面與文字交錯；OrientAI 是有上一項、下一項的橫向片段；導入段是棕褐色半版加步驟條；穩定度是紀錄表；最後是聯絡段。節奏有變化。不一致在大片空白：案例段左欄在兩則案例之間空出約 400–500px；產品段左側約三分之一寬整段都是空的，h2 也不靠左；服務連結列與聯絡段左側也空著。P5 寫明不要「一段文字擠在一側、另一半空著」 |
| D5 證據的呈現 | 4 | 證據是用「紀錄」的樣子呈現：產業段每條事實原文右側有灰字類別標籤（開放銀行、金融檢查、臺北市政府）；案例的成果用大字照原文引用；穩定度段的年份與原文分成兩欄，數字直接寫在 HTML，沒有計數動畫。具名的臺北市政府與華南銀行都以文字出現。沒給 5：案例段的照片面積蓋過成果文字；金融檢查那條事實是一串沒斷句的作業名稱，整段讀起來吃力 |
| D6 窄螢幕 | 3 | 沒有跑版或橫向捲動。hero 在 375 寬重新排過（h1 上半、介面片段、h1 下半靠右、說明與 CTA），第一屏讀得到 h1 與 CTA。產業入口在第 2 屏。但第一則有成果的案例要到約 3,200px（第 4 屏）才看到，超過 brief「兩次捲動內」的要求。產業段右側的類別標籤把事實欄擠成約 230px 的窄欄（臺北市政府那條排成 9 行）。產品段的介面片段右緣被裁掉（例如「主流開源與企業…」） |

要改的地方：

- D2：拿掉導入段「導入前」的另一個顏色或標籤寫法，讓 h2 只有一個樣式。案例段的圖改成和案例本身相關的內容（理賠文件、單據、聯防作業），或縮小面積降成幫腔。介面片段裡的陰影拿掉。原因：這三處各自違反了設計原則與 house rules 的一條
- D3：hero 讓 h1 回到第一眼焦點，例如降低介面欄的亮度或面積，或讓 h1 兩半不要被它隔開。案例段讓成果原文比照片醒目。聯絡段的 h2 要比說明句大。原因：目前次要元素蓋過了 brief 認定最重要的內容（定位、成果、聯絡）
- D4：收掉案例段、產品段、聯絡段左側的大片空白，讓內容填滿格線，或讓空白有目的。原因：P5 明文不要半邊空著的版面，長頁面捲動時會像缺了東西
- D6：375 寬時讓第一則案例的成果更早出現，例如照片縮小或改到文字後面，產業段只露出摘要。產業段的類別標籤改放到事實的上方或下方，不要佔一欄。原因：brief 要求兩次捲動內找到產業入口與一則案例，窄欄也讓事實難讀

### 文案與行銷：平均 4.5

| 項目 | 分數 | 理由 |
|---|---|---|
| C1 定位清楚 | 5 | h1「金融與政府的系統接上 API 與 AI」加上說明「昕力資訊（TPIsoftware）研發並導入自有軟體，把 API、資料與 AI 安全接進既有系統；規範要求直接做在產品功能裡。」合起來說出做什麼、為誰，也說出差異（規範要求做在產品裡、自有產品加導入），和 messaging 的定位句一致。h1 沒有品牌詞，符合 brief「取捨」第 3 項 |
| C2 對受眾的價值 | 4 | 多數段落從讀者的任務或顧慮寫：「專案不必從零設計合規架構」、「決策者不必在產品原廠和導入廠商之間協調」，OrientAI 用「資料會交給外部嗎？不會。」回答顧慮。產品段每個家族都有一句寫解決什麼問題（例如「核心系統與大型主機透過 API 接進來，AI 模型也走同一道 Gateway。」）。沒給 5：產品段每家族底下還有一長串灰字產品名（SysTalk.ai 那串有 9 個），ESGswift 直接貼事實原文（「碳盤查 盤查企業自身碳排放 包括跨地區/廠區/設備/系統CBAM…」），讀起來像功能清單 |

| C5 符合 brief | 4 | brief 的 8 段都有，順序一致；最新文章與新聞已刪，產業只列金融與政府。缺的與多的：一，brief「內部連結」第 4 段要連到產品頁，至少 digiRunner、gadoDIDO、gadoScout、GreenSwift，錨點帶類別詞，但原型的產品名只是灰字，沒有連結；二，第 7 段多了 2011 TPRS、總部地址與據點，brief 沒列，「2005 年創立」也出現兩次；三，第 5 段 brief 寫特色 3–4 項，原型的輪播有 5 項 |

- C6：刪掉第 6 段重複的第二句（或換成這段 brief 列的其他事實），長的事實原文改成可掃讀的排法。原因：重複與黏在一起的清單讓段落讀起來像沒整理過
