## 評審：colour-chapters

評審日期 2026-11-01，由新的 `reviewer` 依 `site-review` 評分。評審沒有讀本目錄的 `README.md`、`sheet.md` 與其他方向；整頁截圖由評審自己用 Playwright（reduced motion，1280 與 375 寬）逐段截取，不在 repo。設計概念階段不判斷通過與否，分數只供選方向。

第一印象：只看第一屏，5 秒內讀得出來。h1「金融與政府的系統接上 API 與 AI」寫了服務對象和做的事，說明句以「昕力資訊（TPIsoftware）」開頭，右側用灰色方塊、橘色圓和「接點」三個標籤畫出「既有系統、接點、昕力接上的部分」。不過 1280 寬右下的大片橘色弧形，配上紫色主要按鈕，色彩組合跟 FPT 首屏的橘色弧加紫藍很像（`competitors/fpt-1280.png`）。文字能分得出來，色塊本身分不出來。

### 設計：平均 3.3

| 項目 | 分數 | 理由 |
|---|---|---|
| D1 第一屏的辨識度 | 4 | 375 與 1280 寬的第一屏都有 h1、說明句、「聯絡業務」和「依產業看方案」，h1 裡就有「金融與政府」，四家競品都沒做到這點（P1）。hero 圖畫的是接點，不是晶片或光流。扣分有兩處。一是橘色大圓弧加紫按鈕跟 FPT 的 hero 顏色相同、形狀相近。二是「既有系統」灰塊裡的小字是 DigiLism 的產品事實（`index.html` 第 42 行），讀者會以為 DigiLism 就是「既有系統」，接點圖的意思反而亂了 |
| D2 與設計原則一致 | 3 | 對得上的地方：hero 沒有 eyebrow；品牌紫只用在 logo、按鈕和聯絡段；第 2 段左邊灰底是「機關原本的防護」，右邊橘底是 digiRunner 的規範，延續中性色代表既有、accent 代表昕力的分法（P3「色彩」）；穩定度段把事實原文在段落裡用底色標出來（P2 允許的「整段文字裡的標示」）；沒有數字動畫。違反的地方：(1) 產品段是四張歪斜擺放、上方放圖的同款卡片，後面又把同四個家族重列一次索引，碰到 P3、P5「不會怎麼呈現」的「同一種卡片加 icon 的格子」與「一排同樣的卡片」；(2) 1280 寬第 2 段左欄在圖片下方空了約 900px 灰底，OrientAI 段右上也空了半屏橘底，碰到 P5「另一半螢幕空著」；(3) 「金融」上方的小字「規範」（第 62 行）是 eyebrow 式的標籤；(4) 影像是 1800 年德文出生證書、1880 年法國苗圃發票、電報機、門鎖，算比喻，不是 P5 要的「這一段的內容」，也讀不成 P3 要的「層、接點、閘道」；(5) 字級除了 5 個 step token，還另外寫了十幾組 clamp 和 vw，例如聯絡段「聯絡業務」是 22vw，超過「全頁最多五種字級」 |
| D3 視覺層級 | 3 | hero、OrientAI 段、聯絡段的焦點都很清楚。案例段的層級倒過來了：古文件照片佔滿整寬，三段合計約 2400px，真正的證據（「節省逾80%人工作業時間」等成果）卻是橘色窄條裡靠右的內文小字，標題 h3 也不大。第 2 段右欄的規範列和左欄的帳冊圖互相搶視線。產品段先被歪斜卡片吸走目光，下面又重複一次同樣內容 |
| D4 版面與節奏 | 3 | 底色依序是白、灰、黑配圖、黑、橘、白、綠、紫、黑，每段版型也不同（雙欄、整寬圖帶、卡片、表單式片段、紀錄段落），節奏有變化。但間距不一致：第 2 段左欄和 OrientAI 段右上的大片空白，跟其他段落的密度差很多。頁長 1280 寬約 10,859px、375 寬約 13,794px，跟原則拿來當負面例子的 FPT（約 11,100px）差不多 |
| D5 證據的呈現 | 4 | 事實照原文引用，連條件一起寫；具名客戶用文字呈現（臺北市政府、華南銀行）。第 2 段用「類別 → 原文 → 箭頭」的列表，穩定度段在一段紀錄文字裡用底色標出每條事實，這兩種都像紀錄，讓人信任。扣分：案例成果被巨幅裝飾圖壓過，見 D3；「金融檢查」那列把整段條列原文接成一長串，掃讀不了；「開放銀行」的類別名稱連出現兩列 |
| D6 窄螢幕 | 3 | 375 寬沒有跑版，h1 兩行，第一屏有說明句和兩個 CTA；案例的圖說和連結也有重新安排。不過接點圖被推到第一屏下方。第一則案例成果大約在 y=3,500px（約第 4.3 屏），沒有做到 brief 和 P5 要的「兩次捲動內看到一則有成果的案例」。產品段在窄螢幕把卡片和索引各堆一次，這段就約 3,300px |

要改的地方：

- D2：產品段只留一種呈現。拿掉歪斜的同款卡片，或拿掉重複的索引，二選一，讓每個家族寫解決什麼問題的那句承擔辨識度。第 2 段左欄與 OrientAI 段右上的空白，要填進該段的內容，或收掉欄寬。拿掉「規範」小標籤。影像要換成這段實際在講的東西（理賠文件、單據、接點的介面片段），不要用年代比喻。全頁字級收斂到五種以內。理由：這幾處正好是原則「不會怎麼呈現」列出的寫法
- D3：案例段把成果原文放大成這一段的焦點，圖片縮成輔助。理由：這段要回答的是「做得到嗎」，現在先被看到的是 19 世紀的花飾
- D4：收掉大塊空白，把頁長往 brief 的 8 段實際需要的長度壓。理由：間距不一致讓長頁面顯得鬆散，而原則把約 11,000px 的長首頁列為不採用
- D6：375 寬要讓第一則案例成果在兩次捲動內出現，例如縮短第 2 段的規範列、縮小案例圖。產品段在窄螢幕不要呈現兩次。理由：這是 brief「受眾與任務」對決策者的明確要求

### 文案與行銷：平均 4.0

| 項目 | 分數 | 理由 |
|---|---|---|
| C1 定位清楚 | 5 | h1 寫了對象（金融與政府）和做的事（接上 API 與 AI）。說明句補上公司名的首次並列寫法、「研發並導入自有軟體」「接進既有系統」，以及差異「規範要求直接做在產品功能裡」，跟 messaging 的定位句一句一句對得上。h1 沒放品牌詞，也沒用「頂尖」「賦能」 |
| C2 對受眾的價值 | 4 | 主要段落都對到受眾任務：規範（DM-1）、案例（DM-2）、資料會不會交給外部（DM-3）、不必在原廠與導入商之間協調（DM-4）、評估長期合作（DM-6）。OrientAI 的「資料會交給外部嗎？不會。」是用決策者自己的問法寫的。扣分：產品索引、OrientAI「統一管控」、ESGswift 那幾處直接貼事實原文的功能條列，沒有轉成讀者得到的結果 |
| C3 證據支撐 | 4 | 抽查 5 條，跟 `facts.yaml` 的 `source.quote` 都一致：`smartclaim-result`、`smartfilling-result`、`company-milestone-2008-finance`、`company-subsidiaries-sg-vn`、`digirunner-nginx-waf`。據點清單也在事實庫裡。主要主張旁邊都有放證據的位置；回覆時間老實寫「待補」，沒有捏造。扣分：hero 把 DigiLism 的產品事實放在「既有系統」標籤下，事實和它要支撐的對象對錯了；「機關原本的防護」這個標題把 digiRunner 的功能事實說成機關原有的防護，換了一層說法 |
| C4 CTA 與轉換路徑 | 4 | 「聯絡業務」出現在 header、hero、頁尾聯絡段，位置固定。聯絡段寫清楚點了會發生什麼：「填寫聯絡表單，說明您的產業、現有系統與想接上的服務，昕力的業務會與您聯絡」。brief 的次要 CTA（依產業看方案、看所有成功案例、認識 OrientAI、關於昕力、產品總覽）都有。扣分：穩定度段的「從既有系統談起」其實連到 `#contact`，但文字看不出是聯絡入口；聯絡段右上的 ↗ 沒有文字 |
| C5 符合 brief | 4 | brief 的 8 段都有，順序也對，產品錨點帶了類別詞（「digiRunner API 管理平台」）。多出 brief 沒有的內容：hero 圖裡的 DigiLism 事實、第 2 段的 Nginx／WAF 列與三段古文件、穩定度段的據點清單，還有產品家族重複呈現兩次。第 2 段從「產業入口，每個產業一句」擴成規範清單，比 brief 預估的長度長很多 |
| C6 語氣與文字品質 | 3 | 標題大多寫答案，不是口號：「規範要求，已做進產品」「產品和導入，同一家負責」。但有幾處寫給審稿人看的後設句或生硬的句子：「每一則都有可以引用的成果」、「成立年份、海外子公司、資安認證與雲端夥伴關係，是評估長期合作風險的資料」、用「接著／往海外／然後／開發流程上／雲端上」把事實硬串成一段的紀錄（「然後 2020年以「TPIsoftware」 邁入國際」空格也不一致），還有意思模糊的「從既有系統談起」 |

要改的地方：

- C6：拿掉跟讀者說「這段是什麼資料」的後設句，改成直接寫讀者能得到的判斷；穩定度的紀錄改成每條事實各自成列，或用更自然的串接；「從既有系統談起」改成說清楚下一步的文字。理由：這幾句是寫給審稿人看的語氣，不是寫給決策者的，跟 messaging「語氣」的「寫結果與風險」不一致
