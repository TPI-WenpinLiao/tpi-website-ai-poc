## 評審：ledger

評審日期 2026-11-01，由新的 `reviewer` 依 `site-review` 評分。評審只看了 `index.html`、四張截圖與 `docs/strategy/` 的依據檔，沒有讀本目錄的 `README.md`、其他方向與任何 review。設計概念階段不判斷通過與否，分數只供選方向。

第一印象：只看第一屏截圖，5 秒內就讀得出這家公司替金融與政府，把 API 與 AI 接進既有系統。第一屏只有白底和文字，用大號襯線 h1，下面一列「產業｜金融」「產業｜政府與公部門」，還寫了具體的規範（開放銀行與金融檢查、共通性 API 規範）。四家競品的第一屏都是影片、手指或光流的大圖（`competitors/gss-1280.png`、`syscom-1280.png`），ledger 換掉 logo 也不會被當成其中一家。弱點是 1280 寬時 h1 右側約四成留白，hero 下方到第 02 段之間也有一段約 130px 的空帶，第一屏的下半部沒有內容。

### 設計：平均 4.0

| 項目 | 分數 | 理由 |
|---|---|---|
| D1 第一屏的辨識度 | 5 | 1280 與 375 的第一屏（`shot-1280-first.png`、`shot-375-first.png`）都完整看得到 h1、說明第一句「昕力資訊（TPIsoftware）研發並導入自有軟體」、兩個 CTA，以及金融、政府兩個產業入口。產業列附的「開放銀行與金融檢查」「共通性 API 規範」說出了跟競品的差別（規範做在產品裡），不只是產業名稱。四家競品的第一屏都靠影像，沒有一家寫出服務對象 |
| D2 與設計原則一致 | 4 | 多數決定指得到原則。P1：第一屏是純文字，h1 最大。P2：證據全頁用同一格式，左側橘紅色條加「產品功能／公司資料」標籤、原文引號、「出處：…」，案例寫成「作業｜成果（案例原文）｜連結」三欄，年份與認證用 mono（第 07 段）。P3：第 04 段結尾的圖 1 分成「既有系統（中性框）→ 昕力的產品（紫框淺紫底）→ 新的服務」，連線與接點用品牌橘紅。P4：沒有 script、沒有動畫，sticky header 上有「聯絡業務」，大面積中性色。輕微違反兩處。P5 要求「字級依段落重要性分級」與「用底色標出三組判斷」，但 02–07 每段的 h2 同字級、同樣的「粗線＋編號＋eyebrow」開頭；灰底只用在第 05 段 OrientAI 和聯絡段，沒有對應「是不是為我做／做得到嗎／安不安心」三組。P2 要求事實與表述在字體上有固定差異，但第 07 段的客戶證言用粗體襯線（跟 h2 同一種字），其他事實都用無襯線 |
| D3 視覺層級 | 3 | hero 的焦點明確，閱讀順序也照 brief 的 1→8。但段落的視覺權重沒有反映 brief 的重要性：brief 與 P5 要 hero、產業、案例三段最重，實際上第 03 段案例表跟第 07 段紀錄列同一個權重，第 04 段產品家族反而最長、最搶眼（四組名稱、連結、證據條並排，375 寬時約 1,700px）。第 04 段右欄四條橘紅證據條跟左欄的家族名稱互相搶第一眼。第 07 段的證言是粗體襯線大段落，比左邊的紀錄列和 h2 下的引言更醒目 |
| D4 版面與節奏 | 4 | 間距一致：每段上緣都是粗線，左側編號欄對齊，同一套格線貫穿全頁。各段版型確實不同（雙欄產業、三欄表格、索引列、架構圖、編號清單、年份紀錄、灰底收束、深色 footer），捲動時不單調。扣分在 1280 寬的留白：hero、第 02 段（內容只到約 800px，右側約 380px 空著）、第 05 段引言都只用左側 2/3，加上 hero 下方的空帶，看起來比較像沒排滿，不像刻意的節奏 |
| D5 證據的呈現 | 4 | 證據容易看到，也像「紀錄」。每條都有類型標籤、原文引號、出處，案例成果放在獨立一欄，前面有一條連續的橘紅豎線。具名客戶以文字出現（「為華南銀行建置 CRM 系統」、證言署名「Dora 徐靜婷｜新光銀行數位資訊部資深經理」）。沒有數字動畫，也沒有 logo 牆。扣分在第 04 段 ESGswift 與第 05 段 01 項：照搬的事實原文是空格分隔的片段（「碳盤查 盤查企業自身碳排放 包括跨地區/廠區/設備/系統 CBAM …」），沒有標點，看起來像抓壞的文字，反而削弱信任 |
| D6 窄螢幕 | 4 | 375 寬是重新安排過的，不是縮小版：第一屏有 h1、說明、兩個並排的 CTA、兩個產業入口。案例表改成每則一張直排卡片（作業→成果條→連結）。圖 1 改成上中下直排，連線換成垂直。證言移到紀錄列之後。第一則案例大約在第二次捲動內出現（約 1,450px）。扣分有兩點：hero 的產業列後面緊接第 02 段又列一次金融、政府，同樣的內容在窄螢幕上連續出現兩次；header 只有「選單」，從 hero 到頁尾約 7,000px 之間畫面上沒有聯絡業務的入口 |

要改的地方：

- D3 視覺層級：讓 hero、產業、案例三段在權重上明顯高於產品家族、服務、紀錄。例如案例段跟其他段用不同的段落開頭與 h2 級別，產品家族降成一份可以掃讀的索引。理由：P5 與 brief 的排序理由要決策者先確認「是不是為我做」「做得到嗎」，現在每段同一權重，第 04 段還最搶眼。第 04 段右欄的證據條、第 07 段的證言也要退到各自主內容的次一級，不要搶過該段的 h2 與主內容

### 文案與行銷：平均 4.3

| 項目 | 分數 | 理由 |
|---|---|---|
| C1 定位清楚 | 5 | h1「替金融與政府，把 API 與 AI 安全接進既有系統」就是 messaging 的短版定位句。說明「昕力資訊（TPIsoftware）研發並導入自有軟體。金融與政府的規範要求直接做在產品功能裡，核心系統不必先汰換。」補上了為什麼選這家（規範做在產品裡、不必汰換，即 DM-1、IT-4），品牌詞在說明第一句，符合 brief「取捨」第 3 項 |
| C2 對受眾的價值 | 4 | 多數段落從讀者的角度寫。第 02 段寫「專案不必從零設計合規架構」。第 05 段用常見問題「資料會交給外部嗎？」回答決策者的顧慮。第 06 段寫「您不必在產品原廠與導入廠商之間協調」。第 07 段的標題「合作之前，先看這家公司的紀錄」直接對到「評估長期合作風險」。產品家族依「要解決的問題」寫。扣分在第 05 段四個特色是事實原文直接列成功能清單（01 項本身就把四件事擠成一句，02 項只有「Token 成本控管」），第 06 段的服務是一串只有名稱的連結，沒有寫讀者得到什麼 |
| C3 證據支撐 | 5 | 依原型的評法，只看主張旁有沒有放證據的位置：02、04、05、06 段的每個主張旁都有固定的證據欄，03 段本身就是證據，07 段每列都是事實。抽查 8 筆，跟 `facts.yaml` 的 `source.quote` 逐字相同：`digirunner-open-banking-fsc`、`digirunner-ndc-spec`、`smartclaim-result`、`smartfilling-result`、`fraud-platform-result`、`company-milestone-2008-finance`、`testimonial-shin-kong-bank`、`aiso-llm-support`。不計分的提醒（交製作階段）：有三處證據只撐住主張的一半。DigiLism 句寫「接上核心系統與大型主機」，旁邊引的是 MCP／AI Gateway 的事實，不是 `digilism-protocol-integration`；SysTalk.ai 句寫「用在客服、文件辨識與流程自動化」，引的是 LLM 支援；GadoSecurity 句的後半「從日誌找出異常與入侵」沒有 gadoScout 的事實 |
| C4 CTA 與轉換路徑 | 4 | 主要 CTA「聯絡業務」出現在 header（1280 寬 sticky）、hero 與第 08 段，符合主要轉換。第 08 段標題「談您的需求，或預約 demo」寫的是讀者的下一步，說明寫清楚點了會怎樣（業務聯繫，安排需求訪談或產品展示）。回覆時間誠實標成「待補」。次要 CTA（看所有成功案例、認識 OrientAI、關於昕力、產品總覽）都在 brief 指定的位置。扣分：375 寬的 header 沒有聯絡入口，hero 之後要捲約 7,000px 才再看到聯絡業務；案例段之後（讀者最可能被說服的位置）也沒有聯絡入口 |
| C5 符合 brief | 4 | 8 段的順序、目的、h2 都對得上 brief，刪掉的新聞段沒有加回來。hero 的次要動作是「依產業看方案」，服務錨點用節點名「AISO 主權 AI」，digiRunner 的錨點帶類別詞，第 07 段有 6 項事實加一則證言（brief 待確認第 1 項允許）。缺：brief 第 4 段要家族名稱連到 `/products/systalk-ai`、`/products/esgswift`，但 SysTalk.ai 與 ESGswift 兩組沒有家族連結（只有 DigiLism 有「看 DigiLism 產品家族」）。圖 1 是 brief 沒有的元素，但有 P3 撐著，算有理由 |
| C6 語氣與文字品質 | 4 | 表述語氣跟 messaging 一致：寫做的事，不用形容詞，用「您」，沒有「賦能」「頂尖」「一站式」這類字，標題是原創，不是照抄現站。扣分在幾處生硬或後設的句子。hero 的 eyebrow「替誰、做什麼」是 brief 的段落名，不是給讀者看的字。第 03 段引言「成果照案例原文列出」、第 07 段引言「每一項都寫在關於我們」都在對讀者解釋頁面的寫法。第 05 段 01 項與 ESGswift 的證據挑了沒有標點的長片段原文，讀起來像錯字 |

要改的地方：無（文案各項都 ≥ 4）。供製作階段參考：去掉後設說明（eyebrow「替誰、做什麼」、「成果照案例原文列出」、「每一項都寫在關於我們」），改寫讀者得到什麼。第 05 段特色與 ESGswift 證據改挑能單獨成句的事實（例如 `orientai-governance`、`orientai-token-cost` 這類短條目，不用多項並排的片段）。補上 SysTalk.ai、ESGswift 的家族連結。375 寬補一個聯絡入口。
